# GitHub Actions Workflow Audit Report

## 1. Audit scope
The audit covered all workflows located in `.github/workflows/` and supporting actions in `.github/actions/` and `boomtick-pkg/.github/actions/`. Specifically checked for flakiness, correctness, performance, and best practices.

## 2. Workflow files reviewed
- `.github/workflows/deploy.yml`
- `.github/workflows/ci.yml`
- `.github/workflows/validate_issue.yml`
- `boomtick-pkg/.github/actions/impact-analysis/action.yml`

## 3. Findings

### Finding: CI Impact Analysis Job Failures Due to JSON Parse Errors

**Severity:** medium
**Priority:** P2
**Workflow:** `ci`
**File:** `boomtick-pkg/.github/actions/impact-analysis/action.yml`
**Jobs affected:** `impact-analysis`
**Evidence:**
- Log excerpt:
  ```
  ❌ Review failed: Could not parse verdict file (artifacts/github-models-code-review-verdict.json)
  ```
- Run: #28787341016

## Problem
In the `impact-analysis` step in `boomtick-pkg/.github/actions/impact-analysis/action.yml`, the script fails and exits with `1` when it encounters an invalid JSON `*-verdict.json` artifact generated by AI tools. A failure to parse the AI output should not hard-fail the entire CI build; it's flaky by nature. Additionally, `jq` output is not suppressed during the parsing error, leading to messy logs.

## Impact
- flaky required checks
- hidden failures
- unnecessary CI cost

## Recommended fix
Update the fallback condition for when the AI verdict JSON parsing fails.
Instead of failing the build with `exit 1` for malformed verdicts, simply log a warning, suppress `jq` errors with `2>/dev/null`, and allow the build to proceed. The memory specifies: "When parsing AI-generated JSON verdicts (like `*-verdict.json`) in bash scripts within GitHub Actions (e.g., `impact-analysis`), suppress `jq` errors with `2>/dev/null` and downgrade malformed parse errors to warnings to prevent fragile CI failures when AI generation is skipped or malformed."

### Finding: GitHub Pages Deployment Exceeds 1GB Limit

**Severity:** high
**Priority:** P1
**Workflow:** `pages build and deployment` (triggering after `deploy.yml`)
**File:** `.github/workflows/deploy.yml`
**Jobs affected:** `pages-build-deployment` (managed by GitHub automatically based on the uploaded `github-pages` artifact from `deploy.yml`)
**Evidence:**
- Run URL: `28795747934`
- Log excerpt:
  ```
  ##[warning]Uploaded artifact size of 1868458772 bytes exceeds the allowed size of 1 GB. Deployment might fail.
  ##[error]Deployment failed, try again later.
  ```

## Problem
The `deploy.yml` action pushes changes to the `gh-pages` branch. When it does so, it copies all files from `dist/` and commits them. It seems some large media files might be included, exceeding the 1GB hard limit imposed by GitHub Pages. Memory specifically mentions: "GitHub Pages branch deployments (e.g., in `deploy.yml`) must exclude large media files (specifically `images/gear/sketches/*.png`) using `rsync --exclude` when syncing PR previews to the `gh-pages` branch to prevent `pages build and deployment` action failures caused by the 1GB artifact size limit."

## Impact
- hidden failures (the `deploy.yml` action succeeds but the actual page deployment fails)
- PR previews and main site updates break.

## Recommended fix
In `deploy.yml`, use `rsync` with `--exclude='images/gear/sketches/*.png'` instead of `cp -r` to copy the `dist-assets` contents to the deployment destination.

## Example change
```yaml
          # 2. Sync build artifacts
          if [ "$DEST_DIR" != "." ]; then
            # Clean sync for branch subdirectories
            rm -rf "$DEST_DIR"
            mkdir -p "$DEST_DIR"
            rsync -a --exclude='images/gear/sketches/*.png' ../dist-assets/ "$DEST_DIR/"
          else
            # Root deployment for main branch
            # We use selective copy to avoid deleting other branch folders
            rsync -a --exclude='images/gear/sketches/*.png' ../dist-assets/ ./
          fi
          touch .nojekyll

          # 3. Handle Main-specific requirements (tech-dancer/ subfolder and SEO)
          if [ "$REF_NAME" = "main" ]; then
            # Also deploy to tech-dancer/ subdirectory for root domain support
            rm -rf tech-dancer
            mkdir -p tech-dancer
            rsync -a --exclude='images/gear/sketches/*.png' ../dist-assets/ tech-dancer/
...
```

### Finding: Long-running jobs in `Deployment Impact Analysis` and `Test-Build`

**Severity:** medium
**Priority:** P2
**Workflow:** `ci`
**File:** `.github/workflows/ci.yml`
**Jobs affected:** `impact-analysis`, `test-build`
**Evidence:**
- Run #28787341016 execution time is around 17-18 minutes in total.
- E2E tests, build and impact analysis steps take the majority of the time.

## Problem
Currently, the pipeline execution time is roughly ~15-18m per run, mainly due to sequential dependency between heavy jobs like `impact-analysis`, `audit`, and `test-build` waiting for `verify-changes` which acts as a serial gate. `test-build` is especially slow because of E2E tests and Playwright environment setup. The memory mentions that `verify-changes` was historically removed in favor of `on.paths` triggers (see `docs/ci-performance.md`) to shorten execution paths. `test-build` running on every single PR also contributes to the time cost.

## Impact
- slower PR feedback

## Recommended fix
1. Explore removing `verify-changes` as a serial gate and rely completely on native `paths:` filters or conditional step evaluation.
2. Ensure pnpm cache and Playwright cache are properly implemented in the checkout step for `test-build` and other jobs.
3. Move `impact-analysis` out to run concurrently where possible rather than waiting for all jobs to complete.
